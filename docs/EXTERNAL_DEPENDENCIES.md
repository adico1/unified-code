# External Dependency Provenance

Issue #8 defines the external boundary required before clean-room
whole-repository regeneration can be attempted. It inventories bytes; it does
not claim those bytes were generated by Unified Code.

The authoritative machine-readable records are:

- [`seed/EXTERNAL_DEPENDENCIES.json`](../seed/EXTERNAL_DEPENDENCIES.json)
- [`seed/EXTERNAL_DEPENDENCIES_SCHEMA.json`](../seed/EXTERNAL_DEPENDENCIES_SCHEMA.json)

Verify the committed inventory without network access:

```bash
python -m unified.dependency_provenance verify
```

The command exits nonzero for missing, changed, duplicate, incompletely
described or undeclared vendored material, a mismatched license, a mutable
source locator, or a bootstrap record that does not point to the canonical
manifest.

| `unified-code-sha256@ed7d5feb` | project originated | `ed7d5febac95a21f8cd3489b76175ecf5ba05a50` | 2 | repository MIT license |

The SHA-256 component is not presented as a third-party dependency: repository
history shows that its current files originated in Unified Code. Its existing
location under `c/third_party` is recorded honestly and its relocation is a
future focused maintenance task.

Every file below `c/third_party` appears exactly once as an artifact. License
files are themselves hashed. The provenance manifest binds the root seed's
existing vendored IDs, paths and legacy license labels to the canonical
dependency and artifact identities without changing the frozen Stage-1 seed
or fixed-point identity. The canonical record supersedes the SHA-256 files'
older `public-domain-or-project` inventory label with verified repository
origin and MIT distribution provenance.

## Inner and outer boundaries

Vendored source bytes are authoritative external inputs at the bootstrap
boundary. Stage 0 consumes none of them. The generated independent C UEM host
and target adapters consume the recorded C artifacts during Stage 1.

CPython, a C99 toolchain, POSIX build tools and the optional Chromium physical
GUI proof are host substrate requirements. They are not mislabeled as vendored
repository bytes. Issue #9 must pin the actual clean-room environment and
record its evidence before claiming whole-repository reproducibility.

GitHub Actions and the setuptools packaging backend are also explicitly
excluded from the vendored-byte inventory. They are orchestration surfaces,
not hidden runtime dependencies of `uc verify-all` or the dependency-free
self-test runner.

## Deliberate limits

This contract does not download, update, replace or generate dependencies. It
does not close the clean-room fixed-point proof by itself. It supplies the
complete, deterministic and offline-verifiable dependency authority required
for that separate integration proof.
