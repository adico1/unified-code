# Vision

Unified Code investigates whether one explicit semantic authority can generate
many exact software products without repeatedly handwriting their shared
structure.

```text
human intent
→ canonical seeds
→ deterministic assembly
→ exact specialized products
→ generated verification
→ observable evidence
```

The practical direction is one construction language shared by people and AI.
Applications keep different identities, interfaces and behavior, while common
parsing, composition, boundaries, rendering, emission and verification remain
one audited infrastructure.

## What is demonstrated

The current application suite assembles 80 products in one operation: 33
calculators, 34 Todo applications, nine Pong products, two document tools, one
math library and one development observatory. The Todo family includes the
generated GitHub Application Atlas planning application. The public build is
grouped by product family and every product retains its authority,
specification, application, generated tests and manifest.

This is evidence that several application families can share an assembly
process. It is not proof that every application is expressible.

## Deterministic AI Pyramid

The longer social direction is a **Deterministic AI Pyramid** in which people
across Earth may contribute code, declarations, evidence and maintenance to
one deterministic construction infrastructure. Standard Ten supplies the
technical base; the Pyramid adds contribution, identity, stewardship and
liveness governance above it.

```text
deterministic laws
→ canonical contributor identities
→ registered contributions and idea claims
→ reusable semantic seeds
→ generated product identities
→ versioned artifacts and deployments
→ measured application liveness
```

The registry must keep different claims distinct:

| Record | Meaning |
| --- | --- |
| contributor identity | one canonical participant identity inside the registry, with separately verified account links |
| contribution | an attributable code, seed, evidence, design or maintenance event |
| idea claim | provenance that one or more people described an idea; not exclusive product authority |
| product identity | the canonical identity of a manifested, reproducible product |
| stewardship | time-bounded responsibility for maintaining a product under declared obligations |
| artifact identity | a content-addressed product version |
| deployment identity | one installation of one artifact |
| liveness observation | dated evidence that an application is active, dormant, archived, unavailable or unresolved |

Several people may independently claim the same idea. That conflict does not
need an invented winner: every claim keeps its provenance. An idea becomes a
product only when a reproducible product manifests it. Product stewardship is
not inferred from an idea claim, popularity or a GitHub account; it is an
explicit, versioned responsibility supported by evidence that the declared
maintenance obligations continue to be met.

The goal of one contributor identity is a registry invariant, not a current
claim that one GitHub account proves one real human. Identity verification,
privacy, pseudonymity, organizations, transfers, disputes, simultaneous
invention and legal ownership require an evolving governance contract. Every
contract version must remain pinned so a new rule cannot silently rewrite old
evidence.

Application liveness is also derived rather than asserted. A future liveness
contract may measure releases, reproducible builds, verified deployments,
voluntary usage evidence and active stewardship. It must distinguish `active`,
`dormant`, `archived`, `unavailable` and `unresolved`; lack of popularity alone
must not make an application dead.

This Pyramid is a direction and governance research program. The repository
does not yet prove a global identity system, ownership adjudication, complete
GitHub acquisition or worldwide application coverage. The current bounded
entry is the [GitHub Application Atlas tracker](https://github.com/adico1/unified-code/issues/41).

## Longer direction

The application proof should progressively converge with the deeper Unified
Code architecture: Standard Ten, Thing v2, UEM, independent Python and C hosts,
name-to-manifestation and ultimately a root-seed fixed point. That final root
claim remains open until one pinned `ROOT.seed` regenerates the complete
repository byte-for-byte.

The engineering vocabulary was inspired by a modern reading of *Sefer
Yetzirah*. The repository does not claim that this reading is the established
historical meaning of the text, nor does it claim measured economy-wide
savings.
